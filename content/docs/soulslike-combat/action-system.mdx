> The brain behind enemy decisions. Scoring every available action and picking the right one for the moment.

<ActionFlowVisualizer />

## When to Use This

- Any AI that chooses between multiple actions (attacks, abilities, retreats)
- Enemies with varied movesets where you want intelligent selection
- Boss fights with phase-based action sets
- Context-aware AI that reacts to player state (blocking, low health, etc.)

> This system can be used independently of the other plugin systems.

---

## Core Concepts

### The Scoring Formula

Every action in your ActionSet gets scored each evaluation:

```
FinalScore = BaseWeight
           × DistanceScore        // Are we at the right range?
           × AngleScore           // Are we facing the target?
           × HealthModifier       // Does our health affect this?
           × NoveltyScore         // Have we used this recently?
           × ChainBonus           // Does this combo from our last action?
           × ContextModifiers     // Player blocking? Low health?
```

The highest-scoring action that's off cooldown and meets requirements wins.

### Distance & Angle Evaluation

Each action defines its ideal range using `FRangeEval`:

```cpp
// Example: Light attack is perfect at 150-250cm, valid up to 400cm
Distance.MinValue = 0;
Distance.OptimalMin = 150;    // Score = 1.0 starts here
Distance.OptimalMax = 250;    // Score = 1.0 ends here  
Distance.MaxValue = 400;      // Invalid beyond this

// Visualization:
//   0    150      250      400
//   |-----|========|--------|
//  0.0   1.0     1.0      0.0
```

Same concept applies to angle. Attacks that require facing the target score higher when aligned.

### Cooldowns

Each action has independent cooldown tracking:

| Property | Purpose |
|----------|---------|
| `Duration` | Time before action can be used again |
| `WarmupCooldown` | Starting cooldown (prevents immediate use on spawn) |
| `RandomDeviation` | Adds randomness to cooldown duration |

### Novelty Decay

To prevent repetitive behavior, recently-used actions get penalized:

- Just used: Score heavily reduced
- A few seconds ago: Score slightly reduced  
- Long time ago: Full score

This creates natural variety without explicit randomization.

### Chain Bonuses

Actions can combo into each other:

```cpp
// In your ActionSet:
LightAttack.PreferredNextAction = "HeavyAttack";
LightAttack.ChainBonusMultiplier = 0.5f;  // +50% score for HeavyAttack if chaining
```

After a LightAttack, HeavyAttack gets a scoring boost, encouraging combos.

## Execution Modes



Actions can execute in two ways:

### Gameplay Ability Mode

For simple actions: play a montage, apply damage, done.

```cpp
FActionSpec LightAttack;
LightAttack.Id = "LightAttack";
LightAttack.ExecutionMode = EActionExecutionMode::GameplayAbility;
LightAttack.AbilityTag = GameplayTag("SEC.Action.LightAttack");
LightAttack.AbilityEndTag = GameplayTag("SEC.Action.End");
```

The system activates the ability via AbilitySystemComponent and waits for the end tag.

### Behavior Tree Mode

For complex multi-step actions with branching logic:

```cpp
FActionSpec ChargeAttack;
ChargeAttack.Id = "ChargeAttack";
ChargeAttack.ExecutionMode = EActionExecutionMode::BehaviorTreeSequence;
ChargeAttack.BehaviorTrees = { BT_ChargeWindup, BT_ChargeRelease };
ChargeAttack.BehaviorTreeTimeout = 5.0f;
```

The system runs each BT in sequence. Use this for:
- Charge attacks with stamina checks
- Multi-hit combos with conditional branches
- Actions that need movement mid-execution

**Auto-populated Blackboard Keys:**

| Key | Type | Value |
|-----|------|-------|
| `SEC_TargetActor` | Object | Current focus actor |
| `SEC_SelfActor` | Object | Controlled pawn |
| `SEC_Distance` | Float | Distance to target |
| `SEC_ActionId` | Name | ID of executing action |

## Role-Based Switching (Advanced)

To automatically swap ActionSets when roles change (e.g., from *Attacker* to *Supporter*), the **SECCombatControllerComponent** handles this automatically.

### How it Works
1.  **AI Config:** Map roles to ActionSets in your `UEnemyAIConfig`.
2.  **Component:** The `SECCombatControllerComponent` on your controller detects role changes from the subsystem.
3.  **Syncing:** When the role changes, the component queries the correct ActionSet and pushes it to the `ActionEvaluationComponent` and `SECActionSetComponent` on the pawn.

### Resolution Order
The component decides which ActionSet to use based on this priority:
1.  **Runtime Override** (Highest Priority - e.g., Boss entering Phase 2)
2.  **Equipped Weapon** (If the weapon implements `ISECWeaponActionSetProvider`)
3.  **AI Config Role** (Specific set for "Attacker", "Flanker", etc.)
4.  **AI Config Default** (Fallback)

> **Pro Tip:** This allows "Weapon-Driven" combat. If an enemy picks up a bow, the weapon can provide a Ranged ActionSet, instantly changing the AI's behavior.

## Dynamic Action Management

Sometimes you need to add or remove individual actions at runtime without swapping the entire ActionSet. For example, an enemy picks up a grenade and gains a "ThrowGrenade" action, or a boss loses a limb and can no longer use "SweepAttack".

Granted actions live in a **separate runtime pool** that persists across role changes and ActionSet swaps. They participate in evaluation alongside the base ActionSet - same scoring, same cooldowns.

### Grant / Revoke API

```cpp
// Grant a single action at runtime
ActionEvaluationComponent->GrantAction(ThrowGrenadeSpec);

// Grant all actions from a data asset
ActionEvaluationComponent->GrantActionsFromSet(DA_BonusActions);

// Revoke by ID
ActionEvaluationComponent->RevokeAction("ThrowGrenade");

// Revoke all actions from a data asset
ActionEvaluationComponent->RevokeActionsFromSet(DA_BonusActions);

// Clear everything granted at runtime
ActionEvaluationComponent->ClearGrantedActions();

// Query
bool bHas = ActionEvaluationComponent->HasGrantedAction("ThrowGrenade");
TArray<FName> Ids = ActionEvaluationComponent->GetGrantedActionIds();
```

### Delegates

```cpp
// React to runtime action changes
ActionEvaluationComponent->OnActionGranted.AddDynamic(this, &AMyClass::HandleGranted);
ActionEvaluationComponent->OnActionRevoked.AddDynamic(this, &AMyClass::HandleRevoked);

void AMyClass::HandleGranted(FName ActionId)  { /* update UI, etc. */ }
void AMyClass::HandleRevoked(FName ActionId)  { /* clean up */ }
```

> **Delegates vs. Overridable Hooks:** Delegates let you *react to* events. For *modifying* behavior (gating which actions can execute, adjusting scores), use the `BlueprintNativeEvent` hooks described below.

### Custom Action Gating & Scoring

The `ActionEvaluationComponent` provides two `BlueprintNativeEvent` hooks you can override in a Blueprint subclass. These let you inject project-specific logic without understanding the built-in scoring pipeline.

**CanExecuteAction** - Custom gate called after all built-in hard gates pass. Return `false` to veto an action.

```cpp
// Override in your Blueprint subclass of ActionEvaluationComponent:
bool UMyActionEval::CanExecuteAction_Implementation(FName ActionId, const FDecisionContext& Context)
{
    // Block heavy attacks during boss phase 2
    if (ActionId == "HeavyAttack" && Context.WorldTags.HasTag(Phase2Tag))
    {
        return false;
    }
    return true; // Allow by default
}
```

**ModifyActionScore** - Called after the built-in scoring pipeline computes a score. Return a modified score.

```cpp
// Override in your Blueprint subclass:
float UMyActionEval::ModifyActionScore_Implementation(FName ActionId, float BaseScore, const FDecisionContext& Context)
{
    // Boost defensive actions when health is low
    if (ActionId == "Block" && Context.HealthPercentage < 0.3f)
    {
        return BaseScore * 2.0f;
    }
    return BaseScore; // No change by default
}
```

These hooks are called during `EvaluateBestAction()` and work alongside the existing `GlobalMultiplier` and `ActionOverrides` runtime modifier API.

### Pawn-Side Convenience

`SECActionSetComponent` provides convenience wrappers that forward to the controller's `ActionEvaluationComponent`. This is useful when Blueprint code has a reference to the pawn but not the controller:

```cpp
// These do the same thing, just accessed from different places:
Pawn->ActionSetComponent->GrantAction(Spec);
Controller->ActionEvaluationComponent->GrantAction(Spec);
```

> Granted actions are independent from the base ActionSet. When the AI changes roles and gets a new ActionSet, all previously granted actions remain available.

## Replicated Action State

The **SECActionSetComponent** replicates key execution state to clients. This is useful for driving client-side visuals like enemy health bars showing the current attack, UI indicators, VFX triggers, etc.

### What Replicates

| Property | Type | Description |
|----------|------|-------------|
| `CurrentActionId` | `FName` | Currently executing action (NAME_None when idle) |
| `bActionExecuting` | `bool` | True while an action is running |
| `ActiveActionSet` | `UActionSet*` | The active ActionSet data asset |

### Client-Side Delegates

```cpp
// Fires on both server and clients when an action starts
ActionSetComponent->OnActionExecutionStarted.AddDynamic(this, &UMyWidget::OnStarted);

// Fires on both server and clients when an action completes
ActionSetComponent->OnActionExecutionCompleted.AddDynamic(this, &UMyWidget::OnCompleted);

// Fires when the active ActionSet changes (e.g., role swap)
ActionSetComponent->OnActionSetChanged.AddDynamic(this, &UMyWidget::OnSetChanged);
```

### Reading State from Clients

```cpp
// Blueprint-friendly getters (work on server and clients):
FName ActionId = ActionSetComponent->GetCurrentActionId();
bool bBusy = ActionSetComponent->IsActionExecuting();
UActionSet* Set = ActionSetComponent->GetActiveActionSet();
```

> The controller pushes execution state to `SECActionSetComponent` automatically. You don't need to do anything special for replication to work - just read the values on clients.

## SEC Play Montage And Wait (Ability Task)

The plugin includes a custom Ability Task called **SEC Play Montage And Wait** - a drop-in replacement for `PlayMontageAndWait` with additional output pins for anim notify callbacks.

### Why?

Standard `PlayMontageAndWait` gives you OnCompleted, OnBlendOut, OnInterrupted, OnCancelled. But if you want to react to specific moments *during* the montage (spawn a projectile at a specific frame, trigger a VFX on impact, etc.), you need custom notify handling.

This task adds **OnNotifyBegin** and **OnNotifyEnd** pins that fire when `PlayMontageNotify` or `PlayMontageNotifyWindow` notify states are hit.

### Output Pins

| Pin | When It Fires | NotifyName Value |
|-----|---------------|-----------------|
| **OnCompleted** | Montage played to the end | `NAME_None` |
| **OnBlendedIn** | Montage finished blending in | `NAME_None` |
| **OnBlendOut** | Montage started blending out | `NAME_None` |
| **OnInterrupted** | Interrupted by another montage | `NAME_None` |
| **OnCancelled** | Task cancelled externally | `NAME_None` |
| **OnNotifyBegin** | A `PlayMontageNotify` or `PlayMontageNotifyWindow` begin | The notify's FName |
| **OnNotifyEnd** | A `PlayMontageNotifyWindow` end | The notify's FName |

### Usage

In your Gameplay Ability Blueprint:
1. Replace `PlayMontageAndWait` with **SEC Play Montage And Wait**
2. Add `PlayMontageNotify` notifies to your montage timeline with descriptive names (e.g., "SpawnProjectile", "ImpactVFX")
3. Wire up `OnNotifyBegin` and switch on `NotifyName` to handle each event

```
SEC Play Montage And Wait (AM_RangedAttack)
  ↓
OnNotifyBegin → Switch on NotifyName
  • "SpawnProjectile" → Spawn and launch projectile
  • "WindupVFX" → Play windup particle effect
OnCompleted → End Ability
OnInterrupted → End Ability (cancelled)
```

> This task supports full GAS replication. Montage plays replicate to simulated proxies the same way standard GAS montages do.

## Quick Setup

### 1. Create an ActionSet

Right-click → Miscellaneous → Data Asset → **ActionSet**

### 2. Add Actions

| Field | Example Value |
|-------|---------------|
| Id | `LightAttack` |
| ExecutionMode | `GameplayAbility` |
| AbilityTag | `SEC.Action.LightAttack` |
| AbilityEndTag | `SEC.Action.End` |
| Distance.OptimalMin | `100` |
| Distance.OptimalMax | `250` |
| Cooldown.Duration | `2.0` |
| BaseWeight | `1.0` |

See [Configuration Reference](/docs/soulslike-combat/configuration#action-sets) for the complete FActionSpec structure.

### 3. Assign to Controller

```cpp
// In AI Controller:
ActionEvaluationComponent->SetActionSet(MyActionSet);
```

Or configure in the [AICombatConfig](/docs/soulslike-combat/configuration#combat-config) for automatic role-based switching.

### 4. Create the Gameplay Ability

Inherit from `GameplayAbilityBase` (required for end detection):

```
Event ActivateAbility
    ↓
PlayMontageAndWait
    ↓
EndAbility  // Automatically sends end event
```

`GameplayAbilityBase` works with **any AAIController**, not just `EnemyControllerBase`. It uses `AAIController::GetFocusActor()` to build the action context (target, distance, direction). If the controller is an `EnemyControllerBase`, it also provides rotation lock during abilities for committed attacks.

> **Important:** Always use `GameplayAbilityBase` as your parent class. It handles the end event automatically. Otherwise, the AI gets stuck waiting.

## Key Functions

```cpp
// Evaluate all actions, return the best one
FChosenAction EvaluateBestAction(const FDecisionContext& Context, float GameTimeSeconds);

// Execute a chosen action
bool ExecuteAction(FName ActionId);

// Swap action set at runtime (e.g., boss phase 2)
void SetActionSet(UActionSet* NewSet);

// Is an action currently running?
bool IsActionExecuting();

// Runtime score modifiers
void SetActionOverride(FName ActionId, float ScoreMultiplier);
void ClearAllOverrides();

// Dynamic Action Management
bool GrantAction(const FActionSpec& Action);
int32 GrantActionsFromSet(const UActionSet* ActionSet);

int32 RevokeActionsFromSet(const UActionSet* ActionSet);
void ClearGrantedActions();
bool HasGrantedAction(FName ActionId);
TArray<FName> GetGrantedActionIds();
```

## Context Tags

Actions can require or block based on gameplay tags:

```cpp
// Only use this action if player is attacking
LightCounterAttack.RequiredTags = {"Player.Attacking"};

// Never use this action if we're enraged
DefensiveRetreat.BlockedTags = {"Self.Enraged"};

// Add these tags while action is active
HeavyAttack.AddTags = {"Self.SuperArmor"};
```
